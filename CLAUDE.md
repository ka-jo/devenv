# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Personal dev environment config with two payloads:

1. **`claude/`** — global Claude Code config (CLAUDE.md, rules, skills, agents, commands, output-styles). `install.sh` (via `lib/link.sh`, also `devenv link`) symlinks `CLAUDE.md` and each child of `rules/ skills/ agents/ commands/ output-styles/` into `~/.claude/` using **relative** links (`../devenv/claude/...`, `../../devenv/claude/<dir>/<child>`).
2. **`devcontainer/`** — the **default dev container config** (`devcontainer.json` + `docker-compose.yml`), used for every `worktrees/<repo>/<branch>` checkout and referenced in place (never copied). Ubuntu 26.04 app container (runs as non-root user `ka-jo`), with tooling from Features: `common-utils` (zsh/oh-my-zsh/sudo/git) and the local `devcontainer/features/fnm` (pinned, checksum-verified fnm + standalone pnpm); Claude Code is still installed by the Dockerfile. The entrypoint makes the worktree's own `.node-version`/`.nvmrc` fnm's default so non-interactive processes get it too. Its sole network is `proxy_net`, an `internal: true` Docker network it doesn't own. `devenv container up/attach` drive the pinned **devcontainer CLI**, never pointed at that file directly: `_container_write_config` generates `~/.local/state/devenv/<project>/.devcontainer/devcontainer.json` from it (mirrored `workspaceFolder`, absolute compose paths, the per-worktree `override.json` appended last) and the CLI runs from that, with `--workspace-folder` set to the state dir rather than the worktree: the CLI only accepts local Features under `<workspace-folder>/.devcontainer/`, and the worktree is agent-writable (local Features are copied there by `_container_write_config`). `down` stays plain `docker compose -p <project> down` (the CLI has no down). VS Code doesn't own the lifecycle — if used, it attaches to an already-running container. Builds run with `BUILDX_BAKE_ENTITLEMENTS_FS=0` (scoped to the CLI call in `_devcontainer`) to work around devcontainers/cli#1320; drop it once upstream ships the fix.
   `devcontainer/infra/` holds the Squid egress firewall + egress-approval broker (`docker-compose.yml`, `firewall/`, `approver/`), run as **one shared instance for every running worktree** (not one pair per worktree), fixed Compose project `devenv-shared`, fixed networks `devenv-shared_external`/`devenv-shared_proxy_net`. Default-deny allowlist is global (single `allowed_domains.txt`/`denied_domains.txt`, not per-worktree), seeded once ever into `devcontainer/infra/firewall/{allowed,denied}_domains.txt` (gitignored) from the tracked `*.default` templates in the same directory. App containers mount `~/devenv` **read-only** (with `worktrees/` hidden behind a tmpfs), so the allowlist is out of a sandboxed process's reach. `firewall/start.sh` watches the allowlist and SIGHUPs Squid to reload it live. Lifecycle is auto-managed by `lib/container.sh` (`_shared_ensure_up`/`_shared_maybe_down` in `devenv container up/down`): started on the first worktree's `up`, torn down when the last worktree's app container leaves `devenv-shared_proxy_net` — derived live from `docker network inspect`, not a counter file. Because Compose `depends_on` can't cross projects, the app container's readiness gate on the firewall is a manual health poll (`_shared_wait_healthy`) in `lib/container.sh`, not `depends_on: condition: service_healthy`.

3. **`dashboard/`** — an Ink (React for CLI) TUI, run on **Bun** (`devenv dashboard`, via `lib/dashboard.sh`), for monitoring worktrees/containers/agents at a glance. Runs on the host only — it shells out to `docker`/`git worktree` directly and needs no devcontainer. Not a port of anything; built from the design handoff in `design_handoff_worktree_dashboard/README.md` (kept outside this repo).

There is no build, test, or lint step for the bash CLI. The repo root is a **Bun workspace** (`package.json` + committed `bun.lock`, isolated linker): `dashboard/` is its one member, and `@devcontainers/cli` is pinned exactly as a root devDependency (its bin runs under the host's Node ≥ 20, not Bun). `install.sh` and `devenv update` run `bun install --frozen-lockfile` at the root. `devcontainer/infra/approver` and `vsc-extension` are deliberately not workspace members — the approver's Docker build context is its own directory, which a root lockfile would sit outside of. Type-check the dashboard with `bun x tsc --noEmit -p dashboard`.

## Hard invariants

- **The repo must live at `~/devenv`.** `install.sh` hard-fails otherwise, and the dev container bind-mounts `~/devenv` at a fixed path. The `~/.claude/*` symlinks are relative so they resolve identically on host and inside any dev container that bind-mounts `~/.claude` and `~/devenv` at sibling paths. Do not change to absolute symlinks.
- **`~/.claude/{rules,skills,agents,commands,output-styles}` are real directories holding per-child symlinks, not symlinks themselves.** Claude writes into them at runtime (e.g. `skills/synced/`); a whole-directory link would leak that into this repo. `devenv link` / `devenv update` / `install.sh` re-sync (and prune dangling links); a new skill/agent/etc. authored in the repo needs one of those to appear.
- **Runtime Claude state is deliberately not symlinked** (`sessions/`, `projects/`, `history.jsonl`, `.credentials.json`, `settings.json`, `cache/`). Stays per-machine. Don't add these to `install.sh`.
- **Per-worktree generated state lives in `~/.local/state/devenv/<project>/`, never inside the worktree.** The worktree is mounted read-write into its container, so anything devenv generates there (e.g. the mount override) could be rewritten by a sandboxed process before the next `up`. The state dir is outside every container mount.
- **The firewall allowlist is global, not per-worktree.** `devcontainer/infra/firewall/{allowed,denied}_domains.txt` (gitignored) is seeded once ever from the tracked `*.default` templates in the same directory, and shared by every running worktree's app container via the single `devenv-shared` stack. Edit the gitignored copy — not the `.default` templates — to change what any worktree can reach. Per-worktree allowlists are an explicitly deferred future enhancement (would need src-IP ACLs in Squid); don't reintroduce per-worktree `.devcontainer/firewall/` files as a shortcut to that.
- **Worktrees are mounted at their mirrored path inside the container (`/home/ka-jo/devenv/worktrees/<repo>/<branch>`), never `/workspace`.** `devenv clone`/`worktree add` use `--relative-paths` (git ≥ 2.48 on host and in the image), and the relative gitdir/backlink pair only resolves when the checkout-to-bare-repo layout is preserved. The bare repo's `config`, `hooks/`, other worktrees' admin dirs, own `commondir`, and the worktree `.git` file are mounted read-only — they're the paths a sandboxed process could otherwise use to get code executed by host-side git. Don't loosen those pins.
- **Container/network isolation between concurrently-running worktrees comes from Compose's project name** (`<repo>-<branch>`, computed in `lib/container.sh` and passed via `-p`), not from string substitution. Don't reintroduce a `__name__`-style sed hack.
- **`bin/` holds only entry points with an external contract** (`devenv`, `claude-wrapper`) — referenced by hardcoded absolute paths from `devcontainer.json`/`Dockerfile`. Only `devenv` gets symlinked onto `$PATH` (never the whole `bin/` dir). Per-subcommand implementation lives in `lib/*.sh`, one file per `devenv` subcommand, sourced by `bin/devenv`.
- **`install.sh` lives at the repo root, not in `bin/`** — it's the one-time bootstrap step run before `bin/devenv` is even on `$PATH`, and keeping it out of `bin/` sidesteps ever having a script named `install` on `$PATH` (it would shadow the coreutils `install` command used by build tooling).
- **`worktrees/<repo>/.git` is always bare, and no branch checkout is "the base repo".** `devenv clone`/`devenv worktree` treat every branch — including the default one — as an ordinary worktree under `worktrees/<repo>/<branch-path>`, symmetric with and independently removable from the rest. Don't reintroduce a non-bare "primary" checkout; it breaks that symmetry and risks accidental commits landing in the wrong place. `worktrees/` contents are gitignored (machine-local); only the empty directory itself (via `worktrees/.gitkeep`) is tracked.

## Adding a new top-level claude config folder

For a new child inside an existing linked directory, run `devenv link`. For a new top-level folder, add its name to the loop in `cmd_link` (`lib/link.sh`) and run `devenv link`. Both are idempotent.

## CLI

- `devenv update` — `git pull` in `~/devenv`, then `devenv link`, then `bun install --frozen-lockfile`.
- `devenv link` — (re)link `claude/` entries into `~/.claude/`; prunes dangling links.
- `devenv install-extension [--skip-build]` — build and install the egress approver VS Code extension on Windows.
- `devenv clone <url> [name]` — bare-clone into `worktrees/<name>/.git`, checkout the default branch as a worktree.
- `devenv worktree add <repo> <branch> [base]` / `rm <repo> <branch> [--force]` / `list [repo]` — manage worktrees under `worktrees/<repo>/`. `rm` also deletes the local branch (`-d`, or `-D` with `--force`).
- `devenv container up <repo> <branch> [--rebuild]` — create/start a worktree's dev container via the devcontainer CLI; regenerates the per-worktree mount override and config (`~/.local/state/devenv/<project>/override.json` and `.devcontainer/`) each run. Never recreates an existing container on its own: if the inputs changed since creation (hash in `created.sha256`), it warns; `--rebuild` recreates. First brings up the shared `devenv-shared` firewall+approver stack if it isn't already running (seeding the global allowlist on first-ever start) and waits for it to be healthy.
- `devenv container down <repo> <branch>` — stop that worktree's stack. Also tears down the shared `devenv-shared` stack if this was the last worktree attached to it.
- `devenv container attach <repo> <branch>` — exec a zsh shell in the running dev container (VS Code can separately "Attach to Running Container" using the same `${COMPOSE_PROJECT_NAME}-devcontainer` container name).
- `devenv container list` — list running devenv-managed container stacks.
- `devenv dashboard` — launch the Ink TUI (`dashboard/`, requires Bun on the host; dependencies come from the root workspace install).

## Commit conventions

Conventional Commits with a scope (this repo has documented scopes — see existing log: `devcontainer`, `scripts`, `claude`, `chore`). Issue refs use `Ref #N` footers, never state-changing keywords.
